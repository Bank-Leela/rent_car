# i18n — the Thai-only interface, and how not to break it

## One locale, one file

The UI is Thai. English was removed on 2026-08-05 (`7291b41 feat(i18n):
Thai-only UI — remove the English locale`), which deleted `messages/en.json`.
What is left:

| Thing | Where | Note |
|-------|-------|------|
| Locale list | `i18n/config.ts:6` | `["th"] as const` — one entry |
| Request config | `i18n/request.ts:6-9` | no cookie/`Accept-Language` negotiation; always loads `messages/th.json` |
| Plugin wiring | `next.config.ts:4` | `createNextIntlPlugin("./i18n/request.ts")` |
| Client provider | `app/layout.tsx:60` | `NextIntlClientProvider` wraps the whole tree |
| Messages | `messages/th.json` | 1,242 strings, 56 top-level namespaces |

So "translate this app" is not a task anyone has. There is no second file to
keep in step and no fallback locale to drift against. `isThaiLocale()`
(`i18n/config.ts:19`) exists only so old call sites still read sensibly; it
returns `true` unconditionally and ignores its argument.

next-intl was kept rather than ripped out because every `t("key")` call site
would have had to change (`i18n/config.ts:3-4`). Treat it as a string table with
ICU formatting, not as a translation system.

One consequence of the wiring above: `app/layout.tsx:46` calls `getMessages()`
and hands the **entire** file to the client provider at `:60`. Every string in
`th.json` is downloaded by every browser on every page, including the admin-only
ones. Nothing in there is per-user or secret today; keep it that way.

## Keys resolve at RUNTIME. Nothing in the build catches a bad one

**This is the sentence that matters.** next-intl v4 can type-check keys through
a `declare module "next-intl" { interface AppConfig { Messages: … } }`
augmentation; this repo has none, so `Messages` falls back to
`Record<string, any>` (`node_modules/use-intl/dist/types/core/AppConfig.d.ts`)
and a message key is just `string` to TypeScript. `npx tsc --noEmit` compiles a
key that does not exist. `npm run build` builds it. `eslint` says nothing. The
failure appears only when a human opens that exact screen, and what they see is
the fully-qualified key path rendered as body text:

```
errors.leadTimeTooSoo        ← what a Thai user sees on the page
```

next-intl's default `getMessageFallback` is `namespace + "." + key` and its
default `onError` is `console.error` (both in `use-intl`'s
`initializeConfig`); neither is overridden in `i18n/request.ts`, which returns
only `locale` and `messages`. Nothing throws. A missing *namespace* degrades the
same way: the namespace is resolved once when the translator is created, and
every `t()` from a translator whose namespace is absent returns its own key
path.

This has shipped at least twice. `003ae04 fix(i18n): driverCalendar.titleStation
was never written, and now cannot happen again` is the commit that finally added
a guard.

## The guard, and exactly what it cannot see

`tests/i18n-keys.test.ts` walks every `.ts`/`.tsx` file under the repo root —
skipping `node_modules`, `.next`, `.git`, `docs`, and anything matching
`*.test.ts(x)` (`:27-35`) — finds each translator declaration, and resolves
every **literal** key against `messages/th.json`. It runs as part of
`make check`. On its own:

```
npx vitest run tests/i18n-keys.test.ts
```

It has three parts: the literal-key walker (`:42`), enum coverage pinned to
`prisma/schema.prisma` (`:80-98`), and header-nav labels (`:102-111`).
`expect(checked).toBeGreaterThan(500)` (`:62`) is a canary — if a refactor
breaks the walker's regex, that assertion fails rather than the suite silently
passing on zero keys.

Its blind spots are real and it says so. Do not assume a green test means the
screen is clean:

| Blind spot | Why | Example in tree |
|------------|-----|-----------------|
| Root translators | The walker's regex (`:49-51`) requires a quoted namespace, so `getTranslations()` with no argument is never registered and none of its keys are checked | `components/app-shell.tsx:46`, `app/login/page.tsx:29`, `app/(requester)/layout.tsx:8`, `app/(driver)/layout.tsx:9`, `app/account/layout.tsx:28` |
| Template-literal keys | `t(\`legend.${key}\`)` cannot be resolved statically | `app/(admin)/admin/calendar/page.tsx:223`, `components/admin/simulate-form.tsx:155` |
| Variable keys | `te(res.error)` — the key is a server-supplied code | `components/admin/leave-range-form.tsx:55` |
| Keys held in data | The literal is in an array, not inside `t(...)` | `components/forms/booking-form.tsx:530` (`labelKey` entries), `lib/nav/role-nav.ts:16` |
| Translators not bound to a `const` | The regex only matches `const x = useTranslations("ns")`; a `t` passed across files is likewise untracked | — |
| ICU argument names | It checks that a key exists, never that its placeholders match the call | — |
| Unused keys | Dead entries in `th.json` are never reported | — |

The enum test closes the biggest dynamic hole by pinning `status.*`, `jobType.*`
and `historyFilters.status_*` to the Prisma enums — that is how
`AWAITING_DOCUMENT` once shipped as a raw key in the requester history filter
(`components/requester-history-client.tsx:166`). Two limits on it:

- `historyFilters` is pinned only for the three terminal statuses the filter
  offers; the other seven sit in an explicit skip list (`:87`).
- The table asserts `values.length > 3` (`:93`) to prove the enum was parsed, so
  a three-value enum such as `Role` cannot be added there without loosening it.

Every **other** computed key family is hand-maintained and unguarded — all of
them happen to be complete today, and nothing keeps them that way:
`calendar.legend.*` (mirrors `BookingStatus`, driven by
`lib/booking/status-style.ts:157` and `app/(driver)/driver/calendar/page.tsx:39`),
`fleet.type_*` (`VehicleType`), `roles.*` and `adminUsers.role.*` (`Role`),
`simulate.jt_*` / `error_*` / `reason_*`, `decisions.filter_*`,
`approverActions.denyPresets.*`. Adding a status to
`CALENDAR_STATUS_LEGEND` without adding the message renders
`calendar.legend.NEW_STATUS` on the calendar.

The nav test exists because nav labels are fully-qualified keys resolved through
a root translator (`lib/nav/role-nav.ts:12-13`), which the walker cannot see.
**If you add a mechanism that resolves keys dynamically, add a test to this file
in the same commit.** That is the whole convention.

## The two APIs

| Context | Import | Call |
|---------|--------|------|
| Client component (`"use client"`) | `import { useTranslations } from "next-intl"` | `const t = useTranslations("fleet")` |
| Server component, page, layout, server action | `import { getTranslations } from "next-intl/server"` | `const t = await getTranslations("fleet")` |

Both are used consistently — all 59 `useTranslations` imports come from
`next-intl` and all 56 `getTranslations` imports from `next-intl/server`, with
no other source anywhere. Server actions are request-scoped, so
`getTranslations` works inside them (`lib/booking/create-booking-action.ts:29`).

A translator is created **per namespace**, and its keys are then relative to
that namespace. The near-universal local naming convention is `t` for the
page's own namespace plus short aliases for the shared ones — `te` for
`errors` (46 declarations), `ts` for `status`, `tc` for `common`, `tt` for
`toast`. Follow it; the walker's regex does not care, but readers do.

Namespaces are flat top-level objects, and only two dotted paths are ever passed
to a translator (`emails.passwordReset`, `bookingForm.weekdays`). The full set:

| Group | Namespaces |
|-------|-----------|
| Shared | `brand`, `common`, `errors`, `errorPage`, `roles`, `nav`, `status`, `jobType`, `toast`, `validation`, `listSearch`, `rangeFilter`, `notifications`, `maps` |
| Auth / account | `login`, `forgot`, `reset`, `account`, `signatureForm`, `emails` |
| Requester | `requester`, `requesterUpcoming`, `requesterDetail`, `bookingForm`, `newBookingPage`, `historyFilters`, `bookingDetail` |
| Approver / admin | `approver`, `approverActions`, `decisions`, `admin`, `adminDetail`, `adminNewBooking`, `adminUsers`, `adminDrivers`, `adminEvaluations`, `adminBatch`, `dashboard`, `deptUsage`, `fleet`, `less` |
| Scheduling | `scheduler`, `roster`, `matching`, `simulate`, `assignForm`, `outsourceForm`, `cancelForm`, `calendar`, `calendarDay` |
| Driver | `driver`, `driverCalendar`, `driverDetail`, `stationDrawer`, `tripForms`, `evaluationForm` |

## Adding a string safely

1. **Reuse a namespace.** Use the one the component already has a translator
   for. A new top-level namespace for a single string is churn.
2. **Add the key to `messages/th.json`,** in Thai. There is no English side and
   no fallback — an absent key is a visible defect, not a graceful degradation.
3. **Call it with a string literal:** `t("newKey")`. Not a variable, not a
   template literal, unless you have no choice — literals are the only thing
   the guard can check.
4. **Name ICU arguments identically in both places:** `"{count}"` in the JSON,
   `t("newKey", { count })` in the call. See the next section for what a
   mismatch looks like.
5. **If the key must be computed** (from an enum, a status, an error code),
   either map the value to a literal key with a `switch`/ternary at the call
   site — the pattern `components/admin/scheduler-board.tsx:161-166` uses — or
   add the namespace to the `it.each` table in `tests/i18n-keys.test.ts:80-98`
   so the enum is pinned to `schema.prisma`.
6. **Run the guard:** `npx vitest run tests/i18n-keys.test.ts`. It reads files
   only and needs no database.
7. **Run `make check`** before you call it done (`AGENTS.md`).

## Server actions return CODES, not sentences

This is the mistake that keeps recurring, and it prints an English identifier —
`vehicleBusy`, `cannotAssignInStatus` — to a Thai user.

There are two conventions in this codebase and you must know which one an
action follows before you render its `error`:

**A. The action returns a bare code.** The client maps it. Used by everything
the scheduler board drives:

```ts
// lib/booking/schedule-actions.ts:45,131
if (!bookingId || !vehicleId) return { ok: false, error: "invalidInput" };
...
if (conflicts.length > 0) return { ok: false, error: "vehicleBusy", conflicts };
```

```tsx
// components/admin/scheduler-board.tsx:156-167 — the correct shape
if (res.error === "vehicleBusy" && res.conflicts?.length) {
  setDropError(t("dropConflictDetail", { detail: … }));   // named conflicts
  return;
}
const key =
  res.error === "noAssignedDriver"     ? "noAssignedDriver"
  : res.error === "cannotAssignInStatus" ? "assignBadStatus"
  : "dropFailed";
setDropError(t(key));                                     // never `res.error`
```

The compact alternative, when the codes are `errors.*` keys one-for-one, is
`te(res.error)` — `components/admin/leave-range-form.tsx:55`. It is unguarded:
a code with no matching key renders `errors.<code>`.

**B. The action already translated it.** `error` holds a Thai sentence and must
be printed verbatim:

```ts
// lib/booking/matching-actions.ts:246
return { ok: false, error: te("vehicleBusy") };
```

`useActionToast` (`components/hooks/use-action-toast.ts:10-13`) assumes form B —
it calls `toast.error(res.error ?? t("genericError"))` with no mapping. Passing
it a form-A result puts the raw code in a toast. When you must bridge, translate
first — `components/forms/driver-edit-form.tsx:64`:

```tsx
toastResult(res.ok ? res : { ok: false, error: te(res.error) }, { success: … });
```

**The related leak: zod messages.** `lib/booking/actions.ts:38` and
`lib/booking/create-booking-action.ts:34` both return
`first?.message ?? te("invalidInput")` — the raw zod issue message. The custom
messages in `lib/booking/schema.ts` are English (`"End time must be after start
time"`, `:225`; `"Specify at least one bus or van"`, `:235`), and the defaults
are worse (`"Required"`, `"Invalid date"`).
`components/forms/booking-form.tsx:606` prints that string straight into the
form's error banner. If you add a zod rule whose message can reach a user, give
it a code and map it through `errors.*` rather than letting zod's prose out.

## ICU arguments

`{name}` placeholders are formatted by `intl-messageformat` (11.2.4, via
`use-intl` 4.11.0). Take `errors.leadTimeTooSoon` —
`"วันที่เริ่มต้นต้องล่วงหน้าอย่างน้อย {days} วันทำการ (ไม่นับเสาร์-อาทิตย์)"`:

| Call | Result on screen |
|------|------------------|
| `te("leadTimeTooSoon")` — values omitted entirely | **`next dev`:** `errors.leadTimeTooSoon` plus a `console.error`. **Production build:** the message with the braces intact — `…อย่างน้อย {days} วันทำการ…` — no error, no warning |
| `te("leadTimeTooSoon", { day: 3 })` — wrong name | `errors.leadTimeTooSoon`, plus a `console.error`, in both builds |
| `te("leadTimeTooSoon", { days: 3 })` | `…อย่างน้อย 3 วันทำการ…` |
| `t("k", { x: 1 })` — extra value, no placeholder in the message | extras are ignored |

Row one is the trap, and it is worse than it looks: use-intl's `formatMessage`
hot path skips ICU compilation whenever no values are passed, so the raw string
goes straight to the screen. The *development* bundle adds a `/<|{/` test that
forces compilation precisely so the missing argument raises — compare
`getPlainMessage` in `node_modules/use-intl/dist/esm/development/format-message/index.js`
with the same function inlined in `…/production/format-message/index.js`, which
tests only `values || /'[{}]/`. **What you see in `npm run dev` is not what the
deployed server renders.** Nothing about either outcome is caught by a test; no
call site trips it today.

One namespace deliberately opts out: `roster.rangeDone` uses `%days%`-style
placeholders substituted with `.replace()` in
`components/admin/leave-range-form.tsx:59-69`, because it reports six
independent counters (`%days%`, `%handed%`, `%released%`, `%codriver%`,
`%review%`, `%rerostered%`). Do not "fix" it into ICU without moving all six.

Rich text (`t.rich`) is not used anywhere. `emails.passwordReset.html` passes
`{linkOpen}` / `{linkClose}` as plain string arguments instead
(`lib/auth/credentials-actions.ts:246`).

## Thai that is not in `messages/th.json`

Grepping `messages/th.json` for a Thai string you saw on screen will sometimes
miss. These are the deliberate exceptions:

| Where | Why |
|-------|-----|
| `app/global-error.tsx:26-38` | It replaces the root layout, so it is outside `NextIntlClientProvider` and cannot call `t()`. Its copy is bilingual and static — see the comment at `:6-10` |
| `app/layout.tsx:36-37` | The tab title and meta description are Thai literals in `metadata` |
| `lib/email/templates.ts` | All ten booking emails are assembled from inline Thai literals; the file imports no translator at all. The one translated mail is the password reset, and it lives elsewhere — `lib/auth/credentials-actions.ts:202,242-246`, using `emails.passwordReset` |
| `public/2 แบบฟอร์ม…e.pdf` | The official faculty request form is a real AcroForm; its Thai wording is baked into the template and `lib/pdf/official-form.ts:11` only fills fields |
| Scattered `aria-label` / `placeholder` | e.g. `components/ui/date-time-picker.tsx:437`, `components/admin/add-vehicle-form.tsx:78` |

**Dates are not formatted by next-intl.** `i18n/request.ts` returns no
`timeZone`, and nothing in the app uses `useFormatter` or `getFormatter`. Use
`formatTh` from `lib/format-date.ts:15`, which bakes in `date-fns`'s `th` locale
so the option cannot be forgotten — twenty-one call sites had already forgotten
it and were printing `Thu 20 Aug 2026` in a Thai-only UI. `TZ=Asia/Bangkok` is
set at the process level and is scheduling-critical (`docs/deployment.md`).
